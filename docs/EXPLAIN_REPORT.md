# EXPLAIN report — PostgreSQL indexes

## Setup

- **Dataset:** 200,000 active sounds generated by `db/seed.py` (`random.seed(42)`), 10 categories, `created_at` spread over 730 days.
- **Server:** PostgreSQL 16.16 on Colima (4 vCPU / 8 GiB), `shared_buffers=128MB`, `work_mem=4MB`, `max_parallel_workers_per_gather=2`.
- **Method:** `scripts/bench.sql` executed 3 times before and 3 times after applying `db/indexes.sql`. Values below are medians of `Execution Time`; buffers are `shared hit + shared read` from the first run of each round. `EXPLAIN ANALYZE` executes the statement and adds profiling overhead (per PostgreSQL docs), but both rounds use the same method.
- **Before state:** only `sounds_pkey`, `generation_jobs_pkey` and the `sounds_prompt_hash_key` unique index. Index creation (7 indexes + `pg_trgm`) took **1.46 s**.

## Before / after

| Query | Median before | Median after | Plan before → after | Buffers before → after |
|---|---:|---:|---|---:|
| **Q1** `category='Explosions' ORDER BY created_at DESC LIMIT 20` | 20.927 ms | **0.101 ms** (~207×) | Parallel Seq Scan + top-N heapsort → Index Scan using `idx_sounds_category_created_at` | 21,725 → 23 |
| **Q2** `tags @> ARRAY['ui','notification','feedback']` | 7.940 ms | **0.368 ms** (~22×) | Parallel Seq Scan → Bitmap Heap Scan + Bitmap Index Scan on `idx_sounds_tags_gin` | 2,909 → 30 |
| **Q3** `title ILIKE '%rusty hatch%'` | 5.289 ms | **1.055 ms** (~5×) | Parallel Seq Scan → Bitmap Heap Scan + Bitmap Index Scan on `idx_sounds_title_trgm` | 306 → 70 |
| **Q4** `SELECT category, count(*) GROUP BY category` | 26.183 ms | **14.726 ms** (~1.8×) | Parallel Seq Scan + Partial HashAggregate → Parallel Index Only Scan + GroupAggregate | 21,670 → 900 |
| **Q5** `title ILIKE '%explosion%' LIMIT 20` | 0.217 ms | **1.843 ms** (regression) | Seq Scan → Bitmap Heap Scan on `idx_sounds_title_trgm` | 26 → 64 |

### One sentence per query

- **Q1:** The composite B-tree on `(category, created_at DESC)` satisfies the `ORDER BY` directly, so the database reads 20 index entries instead of scanning and sorting ~40,000 rows.
- **Q2:** GIN turns array containment into a bitmap lookup, avoiding a row-by-row `tags @>` check over the whole table.
- **Q3:** `pg_trgm` extracts trigrams from the unanchored pattern and narrows candidates to 589 exact-substring rows before rechecking them.
- **Q4:** The partial composite index allows an index-only scan for category counts, cutting buffer pages ~24×, but the aggregate still visits every row so wall time improves less dramatically.
- **Q5:** For an extremely common substring with `LIMIT 20`, a sequential scan stops after a few pages, so the trigram bitmap plus recheck is slower — an index selected by cost estimates is not always faster in practice.

Raw median inputs (ms): Q1 `20.927/20.378/22.334` → `0.259/0.101/0.100`; Q2 `7.940/5.352/15.098` → `0.377/0.368/0.323`; Q3 `3.829/5.941/5.289` → `1.055/1.043/1.246`; Q4 `25.304/26.183/27.267` → `21.439/14.726/14.615`; Q5 `0.158/0.359/0.217` → `1.983/1.768/1.843`. Q2 buffers before varied from 1,347 to 15,956 because `LIMIT 20` stops the scan early; the GIN plan stayed at 30 pages in all three runs.

## Postgres text search vs Typesense

| Query | PostgreSQL | Typesense (alias `sounds`) |
|---|---|---|
| `explosion` | `title ILIKE '%explosion%' LIMIT 20`: **0.217 ms** before / **1.843 ms** after; literal substring, 20 arbitrary rows | `q=explosion`: median **15 ms** (runs 45/17/15/13/14), `found=23331`; ranked hits, 4 facets, typo tolerance, weights `title:3,tags:2,description:1` |
| `rusty hatch` | `title ILIKE '%rusty hatch%'`: **589** exact title matches; Q3 median **1.055 ms** after indexing | `q=rusty hatch`: median **6 ms**, `found=1139` because tokens match across title, tags and description; quoted phrase `"rusty hatch"` → 760 hits in 23 ms |

Postgres is faster for a literal substring with a tiny `LIMIT`, but it gives no ranking, facets or typo tolerance. Typesense does more work because it searches and scores three weighted fields over 200,000 documents; it stays the search API, while Postgres remains the source of truth.

## Reproduce

```bash
# Before (a fresh DB where indexes.sql is not mounted):
docker exec -i eleven-typesense-db psql -U soundsnap -d soundsnap -f - < scripts/bench.sql

# Apply indexes, refresh planner statistics, run again:
docker exec -i eleven-typesense-db psql -U soundsnap -d soundsnap -f - < db/indexes.sql
docker exec eleven-typesense-db psql -U soundsnap -d soundsnap -c "VACUUM ANALYZE sounds;"
docker exec -i eleven-typesense-db psql -U soundsnap -d soundsnap -f - < scripts/bench.sql
```

After these measurements `docker-compose.yml` mounts `db/indexes.sql` as `02-indexes.sql`, so a clean clone starts with the final schema. To re-run the benchmark, drop the indexes in a scratch database first.
